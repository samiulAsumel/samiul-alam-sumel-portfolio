How I build

From Operational Problems to Working Systems

I start with the real workflow, identify where time, data or accuracy is being lost, model the process, and build practical software around it.

01

Observe the Operation

Understand the real operational workflow first. The questions come before any software.

  • Who performs the work?The people who do it today, and where.
  • What information do they use?Documents, records and spreadsheets.
  • What gets repeated?Steps done again for every bill, day or record.
  • Where do errors occur?Manual calculation, copying and missed cases.
  • What depends on Excel, paper or messages?The parts a system could take over.

A Real Example of the Approach

Illustrative summary — no real records or figures are shown.

  1. Operational problem

    The port's billing system creates permanent entries, so customs & freight-forwarding (C&F) agents could not check wharf rent (port facility usage charges) before committing. The result was billing disputes, longer cargo dwell time and repeat trips to the counter.

  2. Operational understanding

    • Cargo and vehicle workflow
    • Billing scenarios
    • Free time
    • Wharf-rent slabs
    • VAT and levy
    • Inside / outside storage
    • Rate changes mid-storage
    • Records and print needs

  3. System approach

    The workflow became structured forms, business rules and calculations, saved bills with live search, a dashboard and print-ready A4 invoices, because agents still work from paper.

  4. Result

    A practical web-based operational system designed around the actual workflow, used at the billing counter to verify charges before final submission.

  1. Operational need

    Vehicle positions across warehouse, shed and yard lived in one person's spreadsheet. When they were away, the team lost visibility.

  2. Vehicle and delivery information

    Daily receipts and deliveries are recorded per location, and the app works offline because terminal connectivity is not guaranteed.

  3. Tracking and records

    Every save is stored as a version-controlled commit, so there is a full history and any earlier version can be restored.

  4. Balance calculations

    Each location's closing balance carries forward as the next day's opening balance, adjusted by receipts, deliveries and transfers, with a holiday calendar for working days.

  5. Search and reporting

    Charts, report sections, Excel export and a keyboard quick-navigation palette.

  6. Result

    A working web system the whole department can check and update, replacing a single-person file.

Engineering decisions

Engineering Decisions

Good engineering is not choosing the most complicated technology. It is choosing an appropriate solution for the actual constraints.

Decision 1 · Port Billing

Business logic in the browser

Problem
Billing needed deterministic calculations from the port’s tariff and operational rules.
Decision
Run the rules as plain JavaScript in the browser.
Why
The estimate appears immediately and works offline, with no backend infrastructure for the calculation itself. Only saved bills sync, through a small Cloudflare Worker.
Trade-off
Right for this calculation workflow. If the need grew to centralised transactional records, complex multi-user workflows or server-side audit, the architecture would need reconsidering.

Decision 2 · CarView

PWA, Worker and GitHub-backed data

Problem
A departmental workflow needed shared, structured records and controlled changes.
Decision
An installable web app with a Cloudflare Worker and GitHub-backed data.
Why
Simple deployment, version history, controlled writes and a lightweight architecture suited this one workflow.
Trade-off
Not a universal database architecture. A higher-volume transactional system would normally call for a conventional database.

Decision 3 · PWA

Installable web apps for operational tools

Problem
Operational tools have to reach staff on ordinary devices without a distribution process.
Decision
Ship them as installable web apps.
Why
Lightweight access, browser-based deployment, an installable experience and a responsive interface, with little to distribute. Port Billing and CarView also keep working offline.
Trade-off
The browser sets the limits, so this suits tools that do not need deep device integration.

Decision 4 · AI-assisted development

AI as an implementation accelerator

Problem
Building software independently takes significant implementation time.
Decision
Use AI-assisted development as part of the workflow.
Why
It speeds up implementation, refactoring, debugging assistance, documentation, code exploration and repetitive work.
