Port Billing Calculator ● LIVE — DAILY USE

Real-time advance wharfrent calculator so C&F agents can verify charges before committing, not after.

⌄
The Problem

The port's billing system creates permanent entries — there was no way for a C&F agent to estimate wharfrent charges before committing to them. That caused billing disputes, excessive cargo dwell time, and repeated trips to the counter just to check a number.

The Users

C&F agents at Mongla Port who need to know the expected charge before final submission, and — indirectly — the billing desk, which now fields fewer disputes over surprise totals.

The Constraints

Had to match the port authority's actual slab/VAT/levy rules exactly — a wrong estimate is worse than no estimate. No access to the port's internal billing database, since this is an advance estimator, not a system of record. Output had to be print-ready A4, because C&F agents still work from paper.

The System

Slab-based charge computation, VAT and levy calculation, inside/outside cargo split, hoisting charge auto-calculation, print-ready A4 output.

Technical Decisions

Plain JavaScript/HTML/CSS over a framework — the whole app is one calculation form, and a framework would add build tooling for no real benefit. Deployed as a static PWA on Cloudflare Pages: no hosting cost, works offline, matches how the billing desk actually operates.

Challenges

Getting the slab/VAT/levy math to match the port authority's real billing system exactly — any mismatch makes the estimate actively misleading to the agents relying on it, worse than not having the tool at all.

Result

In daily use by C&F agents at Mongla Port to verify expected charges before final submission — the evidence is that it's still running there today, not a one-time pilot.

What I Learned

A tool doesn't need a backend to be a real system its users depend on daily — client-side logic was enough because the estimate never needed to persist past the moment it's checked.

carview — Daily Car Balance & Location Tracking ● LIVE — DAILY USE

From one person's private Excel file to a shared, version-controlled tracking system for the whole Traffic Department.

⌄
The Problem

Vehicle positions across warehouse, shed, and yard were recorded in one person's personal Excel file — invisible to everyone else. When that person was unavailable, the whole team lost visibility, creating bottlenecks and a single point of failure.

The Users

Mongla Port Authority's Traffic Department — everyone who needs current vehicle positions, not just the one person who used to own the spreadsheet.

The Constraints

Terminal locations don't guarantee reliable connectivity, so it had to work offline-first. No budget or infrastructure for a hosted database. Needed a real history of position changes, not just a current snapshot.

The System

Offline-first PWA tracking 8 port locations, a Bangladesh Government Holiday Calendar loader, a Chart.js analytics dashboard (7 charts + KPIs), 13 report sections, and Excel export.

Technical Decisions

Used a private GitHub repo as the data store instead of standing up a database — every write becomes a version-controlled commit, which gives a full audit history for free with no database to host or maintain. PWA + offline-first because terminal connectivity isn't guaranteed.

Challenges

Replacing a single Excel file with a shared system without introducing a point of failure worse than the one it replaced — the Worker-proxied sync had to be reliable enough that staff would actually trust it over the spreadsheet they already knew.

Result

Now the Traffic Department's shared, version-controlled tracking system — the single-person Excel dependency it replaced is gone.

What I Learned

Version control can be the actual data layer, not just for code — the "no budget for a database" constraint led to a genuinely different, defensible architecture rather than a compromise.

Client Intake Form ● LIVE — DAILY USE

Turns a scattered email/chat back-and-forth into one structured sheet that becomes the actual scope of the quotation.

⌄
The Problem

Collecting project requirements from a freelance/contract client over email or chat is unstructured — details get missed, and without a written scope, "what was actually agreed" becomes a dispute later rather than a shared reference.

The Users

Freelance and contract clients bringing a new website, online store, or custom software project — before any code gets written.

The Constraints

Had to work for a client who has never touched the tool before — open a link, no account, no install. One form had to flex across very different project types (a shop's brochure site vs. an internal SaaS tool) without turning into a maze. An 18-section form risks losing 20 minutes of typing to a closed tab, with no server to save progress to.

The System

18 sections, gated by an opening "what are you building?" answer — website, online store, custom software, or not sure — that decides which later sections even appear (custom-software projects get user roles, modules, data sensitivity, and hosting questions; a brochure site doesn't). Ends in a declaration step where the client types their name to confirm written engagement terms — scope, quotation, payment, revisions, ownership — before a summary is generated and sent via their own email app.

Architecture

Single HTML file, no backend
localStorage
Debounced draft autosave, private to that browser

Technical Decisions

Kept it a single dependency-free HTML file on purpose — a client should be able to open a link and start typing, with nothing to install or sign up for. mailto: avoids running or paying for a mail-sending service just to receive occasional intake submissions. The draft autosave needed no server or account either — it's just localStorage, debounced and flushed on blur/tab-hide/unload.

Challenges

Branching one form across genuinely different project types without it feeling like a maze — solved by making the very first answer ("what are you building?") gate which sections appear later, rather than showing every client all 18 sections regardless of relevance.

Result

Now the intake step before quoting new freelance/contract work — the same "how do you handle this today" and "why now" questions the form asks clients are the ones that used to get lost in a chat thread.

What I Learned

Putting the engagement terms — scope, quotation, payment, revisions, ownership — directly into the form's own declaration step, instead of a separate contract sent later, means client and freelancer agree on the boundary of the work before it starts, not after a disagreement about it.

≈Used as the intake step before quoting new freelance/contract work — covers everything from a brochure site to a custom internal tool through the same 18-section flow, though exact usage isn't logged.

SalahSync ● LIVE — DAILY USE

Set one anchor — Fajr time and office hours — and the rest of the day's schedule, prayer to sleep, recalculates itself.

⌄
The Problem

Started from a static printed daily-routine sheet. Every time Fajr time shifted with the season, or office hours changed, the whole sheet had to be redone by hand — and a paper sheet can't track whether a prayer actually happened in jamaah, alone, or was missed.

The Users

Just me — this is a personal daily-use tool, not a multi-user product. It's the one I open first every morning.

The Constraints

Had to work fully offline — no prayer-time API, no server. Had to hold a genuinely global settings space (~243 countries, full Bangladesh division → district → upazila) including multi-timezone countries like Russia, the US, and Australia, without breaking the schedule math for any of them. And it needed a real bilingual UI — Bangla and English — not just translated labels bolted on after the fact.

The System

Set a location (or GPS) and office hours once; prayer times are computed client-side with a solar calculation algorithm, and every other block — Tahajjud, Sunnah, jamaah breaks, learning time, sleep — is recalculated around them automatically, per day-type (workday / Friday / Saturday each has its own structure). A tracker logs jamaah / alone / qaza / missed per prayer plus daily amal, with streaks and a weekly chart, and flags the day when something doesn't fit — e.g. sleep falling under target.

Architecture
Settings
Fajr/location + office hours, set once
Schedule Engine
Client-side prayer-time calc + day rebuild, no API
localStorage + Service Worker
Logs/streaks saved locally, app installable and offline
Technical Decisions

Used the praytimes.org solar-calculation algorithm instead of a prayer-times API specifically so the app never depends on a network call to know what time it is to pray. Vanilla JS with ES modules, no framework, no backend — a service worker with a network-first strategy keeps it installable and offline-capable while still picking up the newest version when online. All settings and logs live in localStorage, with a manual JSON export/import for backup since there's no account or server to sync to.

Challenges

Making one Fajr-time input cascade correctly into every other block of the day — across three different day profiles and a genuinely global location dataset with multi-timezone countries — without the schedule engine needing special-case logic per country.

Result

Replaced the static printed sheet entirely. Now the first thing checked every morning — the schedule adjusts itself to that day's actual prayer times instead of needing to be redrawn by hand.

What I Learned

Treating Bangla/English as a real first-class toggle from the start — full UI string tables, not just a translated label here and there — was far less painful than trying to retrofit i18n onto a UI that assumed one language.

≈My own daily schedule since I built it — prayer/amal streaks and weekly stats are tracked locally, though I don't have exported numbers to quote.

World Kitchen Atlas ● LIVE

A culinary encyclopedia that rates its own confidence per dish instead of presenting uncertain food history as fact.

⌄
The Problem

Most recipe content online is thin — an ingredient list with no real history, occasion, or cultural context, and when a dish's origin genuinely isn't settled, most sites just assert one version as fact anyway.

The Users

Public, anonymous visitors browsing world cuisine — there's no login. I don't have exported traffic numbers to quote, but it's a real, publicly reachable site with a working visit counter behind it.

The Constraints

The recipe dataset lives in a private repo and its GitHub token can never reach the browser. Under Next.js's static export mode, the entire build fails outright if any country has zero seeded dishes — so real content had to exist before the site could deploy at all, not after. And a lot of culinary history is genuinely uncertain, so the site had to have a real way to say "we're not fully sure" instead of quietly inventing a clean answer.

The System

Dishes are organized continent → country → dish, with client-side search and browse-by-meal-time. Every entry carries a visible confidence rating — a tick-mark badge from "verified" down to thinner sourcing — instead of presenting every dish as equally certain. Small nations with few well-documented dishes list only what can genuinely be confirmed rather than padding the count. Asia is live today — 7 countries, 280 dishes — with the rest of the world marked "coming soon" rather than faked in. An admin panel (PBKDF2 auth) handles recipe CRUD against the private data repo.

Architecture
Next.js Static Export
Pure static HTML/CSS/JS, no server runtime
Cloudflare Worker
Proxies the private data repo + admin auth/CRUD + visit tracking
Private GitHub Data Repo
One JSON file per country, source of truth
Technical Decisions

The GitHub token that can write to the data repo never leaves the Worker — the Next.js build fetches through it at build time, not the browser at request time. Visit counting runs on a SQLite-backed Durable Object rather than Workers KV, specifically because KV's free-tier write limits can't survive a real per-pageview counter. A cosmetic client-side scraping deterrent (right-click/DevTools blocking) is paired honestly with the protection that actually matters — Cloudflare Bot Fight Mode and WAF rate-limiting — rather than relying on the client-side layer alone.

Challenges

Deciding how to represent food history that's genuinely contested or thinly documented, without either asserting false precision or making the whole site read as unreliable — solved by making confidence a visible, per-dish rating instead of a hidden editorial judgment call.

Result

Live today with real, sourced content for Asia — 7 countries, 280 dishes — rather than a thin dataset dressed up to look complete. Europe, Africa, the Americas, and Oceania are the next phases.

What I Learned

On a content-heavy project like this, sourcing and verifying real information is the actual bottleneck, not the code — and being upfront about what isn't confirmed holds up better long-term than presenting a thin dataset as a finished, authoritative record.

≈Asia is live with 280 dishes across 7 countries, each with a visible confidence rating — the rest of the world is planned, not faked in, and I don't have exported visit numbers to quote.

03 / How I Work

How I Build

“

A job starts with a conversation, not a keyboard. I ask what the workflow looks like today, where people lose time to a manual step, and what "done" needs to mean for them — then I write that down as a plain-language requirement and confirm it back before any code gets written. From there, every project on this site was built with AI assistance. That's a plain fact, not a confession — Claude and similar tools are part of how I get from a requirement to working code. But using a tool isn't a skill. The skill is the workflow around it: getting the requirement right, testing what the tool produces, and being able to explain every part of it clearly.

Working From Requirements
Talk First, Build Second

Before any design or code, I go through what the person or team actually needs — what the current process looks like, who touches it, and where it breaks down. That conversation becomes the spec.

Automate The Manual Step

For a company or industry client, the goal is almost always the same: find the part of their running process still done by hand — a paper form, a shared Excel sheet, a recalculation someone repeats every day — and replace it with a deployed tool the whole team can use. That's exactly what portbill, otbill, and carview do for port operations at Mongla; the same approach applies to any workflow with a manual bottleneck.

Solve The Problem, Not Just The Request

A website or dashboard is the deliverable, but the actual job is closing the gap the client described — if the stated request doesn't fully solve it, I say so before building it anyway.

"Build me a billing app" gets a weak result from any model. Business rules, the real data model, edge cases, and acceptance criteria stated up front get an accurate one — I treat specifying that context as its own deliberate skill, not an afterthought.
